# Design — Per-Element stats, repo LOC sizing, and surviving-LOC contribution metric

Date: 2026-06-23
Status: Approved (pending spec review)

## Motivation

Stakeholder feedback on the Constructor Fabric contribution report:

1. "Will be good to see — **by Element**" (per product line: Insight, Studio,
   Gears, …). Today the report only classifies repos as platform-vs-app, with no
   product grouping.
2. Show stats (**KLOC / people / PRs / other**) for Constructor **Insight**,
   **Studio**, and **Gears**.
3. Show **repo size in LOC** in the repo inventory.
4. **Change the contribution metric.** Quote: contribution "should be measured
   mostly by the final code size person created, not by number of commits
   (because some people commit in fabric repos while others — e.g. most of
   Partner Ltd — do the preparation work in internal repos and commit the final
   result), not by number of LOCs generated (people sometimes just regenerate
   the same LOCs). And we should count LOCs of specs and LOCs of code
   separately."

## Decisions (confirmed with stakeholder)

- **Primary contribution metric = surviving LOC** computed by `git blame` over
  each repo's current default-branch tree. Only lines that still exist count;
  the last author of each line wins. This automatically defeats the
  "regenerate the same LOCs" inflation: regenerating a file does not increase
  the total surviving line count, it just reassigns authorship of those lines.
  - **All-time snapshot is the headline ranking** ("how much of today's
    codebase did each person write").
  - A **windowed** companion column ("surviving lines whose last-touch commit
    is inside `lookback_days`") is also shown, for recent-activity signal.
  - Commits and raw windowed additions are **kept but demoted** to secondary
    columns, for continuity.
- **Spec LOC and code LOC are counted separately** everywhere. A file is a
  *spec* per the existing `specs:` denylist (`make_is_spec`), *code* per the
  existing `meaningful_loc` denylist (`make_is_meaningful_loc`). Generated /
  vendored / lockfile / binary paths are excluded from code LOC by that filter,
  so machine artifacts never inflate the metric.
- **Surviving code LOC is split into hand-written vs AI-generated** per person.
  Ranking is on **hand-written** surviving code LOC. AI-generated surviving LOC
  is a separate column (not removed), so AI-assisted ownership is visible
  without crediting regeneration as authorship. Detection of AI-generated lines
  reuses the existing `studio_provenance` markers (`@cpt-begin/@cpt-end`
  regions, `studio: true` spec files, `Generated by cf/cfs` stamps) and is
  badged **heuristic**.
- **Element = full taxonomy.** Every repo maps to exactly one named element; no
  catch-all "Other" bucket. Element is orthogonal to platform/app (a repo keeps
  both classifications).
- **Per-element block shows:** Code KLOC, Spec KLOC, people (members /
  external), repo count, windowed commits, PRs opened / merged, median
  time-to-merge, AI%.
- **Scope of LOC measures:** repo size and surviving-LOC are computable only for
  repos that are **cloned**, i.e. the primary org `your-org`
  (~28 repos). The old `your-old-org` org is not cloned; its repos contribute
  only PR / people / issue metadata, which still rolls up into their element.
  The Elements view and inventory must make this asymmetry explicit (old-org
  repos show "—" for LOC, not 0).

## Rate-limit detection & reporting (added 2026-06-23)

Today the GitHub client (`ghclient.GH`) handles throttling in `_throttled`, but
on a **primary** quota exhaustion whose reset is far away it only sleeps a capped
90s and then keeps retrying; `paginate`/`graphql` ultimately either crash via
`raise_for_status()` or return silently partial/empty data. There is no signal
that the report is incomplete because we ran out of API budget.

Requirement: **detect rate-limit exhaustion and say so**, instead of crashing or
silently degrading.

Decisions:

- **Distinguish, don't conflate.** A `403` from `/traffic/*` ("must have push
  access") is *not* a rate limit — `_throttled` already returns `False` for it;
  keep that. Only `X-RateLimit-Remaining: 0` (primary) or a secondary/abuse
  message (`Retry-After`, "secondary rate limit", "abuse") count as throttling.
- **Bounded wait, then give up cleanly.** Primary limit with `reset - now`
  within a configurable `api_max_wait_seconds` (default 90) → sleep and retry as
  today. Beyond that → record the event, set a sticky `GH.rate_limited` flag and
  `GH.rate_reset_epoch`, and stop retrying that call (no infinite/futile spin,
  no multi-minute hang).
- **Graceful partial, never a crash.** When `GH.rate_limited` is set,
  `paginate` breaks and returns what it has (and does **not** cache the partial
  result, so a later run with refilled quota completes it); `graphql` returns
  `{}` instead of raising. The sticky flag is the single source of truth.
- **Surface it.** `collect.py` writes an `api` block into `data.json`
  (`rate_limited`, `rate_events`, `reset` ISO, `core_remaining`/`core_limit`,
  `search_remaining`) and prints a clear `WARNING: GitHub API rate limit hit …
  data is PARTIAL … resets at <iso>` to stderr. `render.py` shows a prominent
  banner in the Overview trust surface when `api.rate_limited` is true and counts
  it as a trust gap (`risk_count`).
- **Config:** `api_max_wait_seconds` in `config.yaml` (default 90).

## Architecture

```
config.yaml (elements:, reuse specs:/meaningful_loc:/studio_provenance:)
   │
   ▼
collect.py
   ├─ make_element(cfg)            # repo name -> element
   ├─ full-tree blame pass         # per cloned repo, per meaningful/spec file
   │     reuses & generalizes blame_marker_authors
   │     -> per (login, element, repo, kind{code,spec}, origin{human,ai})
   │     -> repo size (code_loc / spec_loc / total_loc) as byproduct
   │     -> blob-SHA cache in .cache/blame/<repo>/<blob>.json
   ▼
data.json
   ├─ repos[].element, repos[].code_loc/spec_loc/total_loc
   ├─ people[].surviving_code_human / surviving_code_ai / surviving_spec_loc
   │            + windowed survwin_* variants
   └─ elements{}: rollup per element
   ▼
render.py
   ├─ new "Elements" section/tab
   ├─ Repos inventory: + Element, Code LOC, Spec LOC, Total LOC columns
   └─ People table: re-ranked on hand-written surviving code LOC
```

### collect.py changes

- `make_element(cfg)` — classifier mirroring `classify()`; returns element name
  for a repo name, `default` if unmatched. Stored on repo meta and in
  `data.json` repos.
- **Full-tree blame pass** (generalize `blame_marker_authors`): for each cloned
  repo, list the current tree (`git ls-tree -r --name-only <ref>`); for each
  path where `is_meaningful_loc(path)` (→ `code`) or `is_spec(path)` (→ `spec`),
  run `git blame --line-porcelain <ref> -- <path>`. For each line:
  - resolve author email → login via the existing identity resolver;
  - `kind` = code or spec;
  - `origin` = `ai` if the line is inside a `@cpt-begin/@cpt-end` region, OR the
    file is a `studio: true` spec, OR the file carries a `Generated by cf/cfs`
    stamp; else `human`. (Region detection: scan file lines once for the marker
    pairs; lines between an open/close marker are `ai`.)
  - accumulate counters keyed by `(login, kind, origin)` and per-repo size, and
    record the line's last-commit date for the windowed variant.
- **Caching**: key each file's blame result by its blob SHA
  (`git rev-parse <ref>:<path>` or from `ls-tree`); store
  `.cache/blame/<repo>/<blob>.json`. Unchanged blobs are read from cache, so
  re-runs only re-blame changed files. `.cache/blame/` is already covered by the
  `.cache/` gitignore entry.
- **New per-person fields**: `surviving_code_human`, `surviving_code_ai`,
  `surviving_code_loc` (=human+ai), `surviving_spec_loc`, and windowed
  `survwin_code_human`, `survwin_code_ai`, `survwin_spec_loc`. Existing
  `commits`, `additions`, `meaningful_additions`, `cpt_lines` retained.
- **New per-repo fields**: `element`, `code_loc`, `spec_loc`, `total_loc`
  (null for non-cloned old-org repos).
- **New `elements` rollup** in `data.json`: per element — code_loc, spec_loc,
  people (members/external distinct contributors), repo count, windowed commits,
  prs_opened, prs_merged, median_ttm_h, ai_pct.

### render.py changes

- **Elements section** (new tab, also tagged `all`): one row per element sorted
  by Code KLOC; columns Code KLOC, Spec KLOC, People (members / external),
  Repos, Commits (window), PRs opened / merged, Median TTM, AI%. Old-org-only
  elements still appear with LOC shown where any cloned repo exists.
- **Repos inventory**: add `Element`, `Code LOC`, `Spec LOC`, `Total LOC`
  columns; non-cloned repos render LOC as "—".
- **People table**: primary sort = hand-written surviving code LOC. Columns:
  Hand-written code LOC, AI-gen code LOC, Spec LOC, Surviving Δ (window), then
  secondary Commits / Raw additions. Precision badges: surviving LOC = **exact**
  (real git data); human/AI split = **heuristic**.

## Testing

Add to `tests/test_rules.py`:

- `make_element`: confident mappings for both orgs, the `default` fallback for
  an unmapped name, and orthogonality with `classify`.
- Blame line-classification: a fixture tree where one file is code, one is a
  spec, one is excluded (lockfile / generated) — assert code/spec/excluded
  counts.
- Origin split: a fixture file with a `@cpt-begin/@cpt-end` block and lines
  outside it — assert ai vs human line counts; a `studio: true` spec file → all
  spec lines ai.
- Element rollup: given synthetic per-repo data, assert element aggregation
  (LOC sums, distinct people, PR sums) and that non-cloned repos contribute
  PR/people but not LOC.

Compile/sanity: `python -m py_compile` on changed modules and
`python -m unittest discover -s tests`.

## Out of scope

- No new data source for internal/preparation repos (the Partner Ltd "prep work in
  internal repos" case is acknowledged in motivation but is unobservable from
  GitHub; the surviving-LOC metric mitigates it by crediting the final committed
  result rather than commit count, which is the available lever).
- No change to identity resolution, traffic, or review panels beyond consuming
  the new per-element rollups.
- No historical backfill of surviving-LOC trend; current snapshot only.

## Performance note

First run blames every meaningful/spec file across ~28 cloned repos — minutes,
not seconds. The blob-SHA cache makes subsequent weekly runs near-instant for
unchanged files. Blame is parallelizable per repo if needed (existing
`spec_fetch_workers`-style pool), but start single-threaded with caching and
measure before optimizing.
